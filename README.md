# Beat Agent

My submission for the Soundverse Applied AI Engineer assignment: one chat-driven agent
that works with audio in three ways.

1. **Beat alignment and sync.** Finds tempo, beats, downbeats and meter, writes a beat
   grid, exports a click track to check it by ear, and beat-matches track B onto track A
   with pitch preserved.
2. **Chat editing on the grid.** Requests like "cut beat 16-32 and repeat it twice" are
   turned into typed edit operations. Code checks them, tells you exactly what it is about
   to do, and applies them with crossfaded splices.
3. **Audio to playable code.** A short loop becomes a score (JSON) and a single HTML
   page that plays it back with Web Audio synthesis.

The rule I kept throughout: the LLM only interprets what the user typed. Tempo, beat
times, notes and offsets all come from signal processing and models (Beat This!, Basic
Pitch), never from the LLM.

## A note on test data

The A1–A7 and P1–P4 test pack wasn't included with the brief, so I built synthetic
versions from its descriptions (`evals/part1/make_testpack.py`,
`evals/part3/make_p3pack.py`). Because I generated them, the answers are exact. All the
target numbers in this README come from those synthetic clips, and they're labelled that
way in the app and in every report.

The evals will run on the real pack as is:

```bash
python run.py eval --pack testpack                  # Part 1, audio + beat files in data/testpack/
python -m evals.part1.eval_sync --pack testpack
python -m evals.part2.eval_sessions --pack testpack --llm gemini
python -m evals.part3.eval_part3 --pack data/testpack   # clips, with <clip>.mid where available
```

Run `eval` first, because the sync step reuses its grids. Part 3 clips without a MIDI
file still get rendered and timing-checked, just not note-scored.

## Running it

### One command

With Docker (uses your own key from `.env` or the shell):

```bash
cp .env.example .env        # add GEMINI_API_KEY
docker compose up --build
```

Or without Docker, on Python 3.11:

```bash
make demo                   # macOS / Linux
python run.py demo          # Windows (after the setup below)
```

All three do the same thing. They download the Beat This! checkpoint, build both
synthetic test packs, run the test suites and the Part 1 and Part 3 evals, then start the
app on http://localhost:8000. Results are written to `evals/results/`. Use Chrome or
Edge for the app.

To start only the app in Docker: `docker compose run --service-ports beat-agent python run.py app`.

The chat needs a Gemini key. Without one, everything else still works, and chat falls
back to a small offline rule parser. Every reply says which of the two answered it.

### Manual setup (Windows, as developed)

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
pip install --no-deps basic-pitch==0.4.0
copy .env.example .env
```

`basic-pitch` goes in with `--no-deps` because its default dependencies pull in
TensorFlow (~400 MB), and the bundled ONNX model only needs `onnxruntime`. Part 3's
offline render drives the installed Edge or Chrome through Playwright; on Linux,
`playwright install chromium` works too. The built UI is committed in `frontend/dist`, so
Node is only needed if you change the frontend (`python run.py ui`).

### Other commands

| Command | What it does |

## How it's built

```
audio ─► beats/analyze.py ─► BeatGrid ─┬─► click.py    click audition
         Beat This! + grid fit          ├─► sync.py     Rubber Band stretch, downbeat alignment
                                        └─► session.py ◄─ edl.py   typed ops, crossfaded pieces
chat  ─► agent.py ─► llm.py (Gemini → Plan) ─► validators ─► session ─► reply / undo / redo
clip  ─► transcribe.py ─► score.py (Score JSON) ─► webaudio.py ─► page.html
```

- `beatagent/core/`: audio I/O, onset detection, the beat grid, quality checks
- `beatagent/beats/`: Part 1, covering analysis, click audition, time-stretch and sync
- `beatagent/editing/`: Part 2, covering the edit engine, session with undo/redo, the chat agent and the LLM interface
- `beatagent/recreate/`: Part 3, covering transcription, the score format, the page template and chat edits on the score
- `app/server.py`: FastAPI backend; `frontend/`: React + TypeScript UI with two decks
- `evals/`: evaluation scripts grouped by part, with results in `evals/results/`
- `tests/`: deterministic tests

The LLM returns a structured plan: an action plus typed operations, validated with
pydantic. Code then works out the bars and beats on the measured grid, states the exact
range in bars, beats and seconds, and either applies the plan or refuses with a reason.
Some guards exist because the LLM got things wrong in testing. For example, it rewrote
"remove bar -2" as bar 1, and it once deleted the entire track for "remove everything".
`DECISIONS.md` covers these.

## How commands are read

- Beats are counted from 0, and a beat range excludes its end: "beats 16-32" is 16 beats.
- Bars are counted from 1, and a bar range includes its end: "bars 9-12" is 4 bars.
- "Repeat it twice" means two plays in total. The reply always states which reading was used.
- Subjective requests ("chop out the boring part") get a proposal based on measurements,
  and nothing changes until you say yes. The same goes for any edit that would leave less
  than 2 seconds of audio.
- Tempo is reported between 80 and 160 BPM; each deck has ½× / 2× buttons to change that.

## How it's measured

- **Beats:** `mir_eval` F-measure at ±70 ms over the whole track, plus AMLt and the
  per-beat distance from the reference.
- **Sync:** each kick pasted into the render is an exact copy of B placed at a known
  time, so the offsets are calculated, not detected.
- **Clicks:** energy above 6 kHz at each splice, compared with the same windows in the
  source. `tests/test_click_metric.py` checks the metric against hard cuts, to make sure it
  can actually catch a click.
- **Part 3:** `mir_eval` note F (onset ±50 ms, pitch ±50 cents) against the reference
  MIDI, plus onset agreement between the offline render and the original.

## Known issues

1. **Sync on real music isn't proven to 5 ms.** On synthetic pairs I have exact answers.
   On real hip-hop my kick detector reads 12–17 ms even when a track is synced to itself,
   so it can't settle the question. The renders need to be judged by ear.
2. **Part 3 struggles on dense mixes.** There's no source separation, so P4 scores 0.51
   (drums) and 0.68 (pitched). Drum classes come from frequency-band rules, not a trained
   classifier.
3. **Live drift.** On A3, 98% of beats are within 10 ms after drift correction, but the
   worst single beat is still 89 ms off.

Smaller ones:
- Telling 6/8 from 12/8 depends on the kick accent, and falls back to the tracker when
  the accent is unclear.
- The only real music I tested on was hip-hop.
- The preview pane in the Claude desktop app won't run the recreation page, so use Chrome
  or Edge.

## Security

- The API key lives only in `.env`, which is git-ignored and excluded from the Docker
  image. It's used server-side, and the frontend never sees it.
- Uploads: file names are sanitised, only WAV, MP3 and FLAC are accepted, and errors
  never reveal server paths. The server listens on localhost unless `HOST` is set (the
  Docker image sets it so the port can be published).
- Generated pages are built from a fixed template. The score is embedded as escaped
  JSON, track names are inserted as text, and the page runs under
  `Content-Security-Policy: default-src 'none'` in a sandboxed iframe.
- LLM output is treated as data and validated against a schema. It is never executed.
